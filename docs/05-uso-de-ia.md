# 5. Uso de assistentes de IA

| Entrega | O que foi pedido | O que o assistente sugeriu | Decisão da dupla | Motivo |
|---|---|---|---|---|
| **1. Modelagem do domínio** | Pedimos ajuda para definir os Bounded Contexts, pois estávamos em dúvida se *Notificações* e *Faturamento* deveriam ser contextos separados da *Garantia*. | O assistente sugeriu dividir em 6 contextos distintos e propôs o agregado de *ConcessaoCredito* com a regra de teto. | Aceitamos a divisão arquitetural, mas reescrevemos a Linguagem Ubíqua com nossas próprias palavras. | A separação sugerida isolou perfeitamente as responsabilidades de mensageria e emissão de notas financeiras da regra principal. |
| **2. Arquitetura** | Perguntamos qual protocolo seria ideal para suportar a perda de pacotes da Telemetria (RNF01) e como resolver de forma simples a idempotência (RF09). | Sugeriu usar UDP para a Telemetria e aplicar uma *Unique Constraint* no banco de dados para rejeitar processamentos duplicados. | Aceitamos as sugestões tecnológicas e adicionamos por conta própria a justificativa de não usar o padrão Observer em memória. | O protocolo UDP faz todo sentido técnico para GPS intermitente. A solução de banco para idempotência evitou complexidade desnecessária no código. |
| **3. Plano de testes** | Pedimos ideias de valores-limite para cobrir as regras de horas do RF02 e exemplos de dublês de teste aplicáveis ao nosso cenário. | O assistente listou os 5 primeiros casos de teste focando nos limites de 2h00 e 2h01, e sugeriu usar Stub na Telemetria. | Aceitamos os casos de borda sugeridos, e derivamos nós mesmos os outros 7 casos para completar os 12 exigidos. | Os valores sugeridos ajudaram a eliminar as dúvidas sobre a regra matemática do negócio, e o Stub isolou perfeitamente os testes. |
| **4. Tela do Portal** | Como atualizar a tela do React ao vivo com a posição do veículo e o saldo do crédito sem sobrecarregar a API com *polling*? | Sugeriu o uso de conexões persistentes com *WebSockets* ou *Server-Sent Events (SSE)*. | Decidimos consolidar na nossa documentação o uso do SSE. | O SSE atende bem ao requisito de forma unidirecional (servidor para cliente) e é mais leve que o WebSocket para apenas receber *pushes*. |
| **5. Implementação** | Pedimos um esboço de como aplicar o padrão *Strategy* em Python para isolar as regras por tipo de cliente (RF04). | Gerou o esqueleto das classes `RegraCalculo` com as interfaces para Varejo, Corporativo e Cortesia. | Usamos a estrutura de interface gerada pela IA, mas nós mesmos escrevemos a lógica matemática interna, os IFs e os casos no `pytest`. | O padrão fornecido atendeu ao princípio *Open/Closed*, garantindo que um novo cliente futuro possa ser adicionado sem alterar nosso código atual. |
